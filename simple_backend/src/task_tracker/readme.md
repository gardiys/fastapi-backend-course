
 ~Хранение состояния — это способ сохранения текущих данных приложения между запросами и
перезапусками. Примеры состояния: список задач, информация о пользователе, текущая сессия.
 ~Минусы хранения задач в оперативной памяти (в списке Python):
Все данные теряются при перезапуске сервера.
Нет доступа к задачам с других устройств или экземпляров сервера.
Невозможно отследить историю изменений.
Трудно масштабировать приложение.
Уязвимо к ошибкам при одновременной работе нескольких пользователей (race condition).

 ~Что улучшилось после того, как список из оперативной памяти изменился на файл проекта?
Задачи теперь сохраняются между перезапусками сервера. Данные не теряются, как это было 
при хранении в оперативной памяти.
 ~Избавились ли мы таким способом от хранения состояния или нет?
Нет. Состояние всё ещё хранится локально, не в памяти, а в файле.
Это всё ещё stateful-подход.
 ~Где еще можно хранить задачи и какие есть преимущества и недостатки этих подходов?
1) SQLite - Встроенная БД, не требует сервера. Слабо подходит для многопользовательских
систем.
2) PostgreSQL - Масштабируемость, транзакции, ORM. Требует настройки и деплоя.
3) Облачные API(jsonbin.io, mockapi.io) - Stateless, удобно для тестов и внешнего доступа.
Зависимость от сервиса, лимиты, медленнее.

 ~Проблемы текущего состояния backend

На данном этапе backend использует простой JSON-файл `tasks.json` для хранения задач.
Это небезопасно в многопоточном или многопользовательском режиме, так как может произойти
состояние гонки. Например, одновременное изменение и удаление задачи может привести к
потере данных.
Для устранения этой проблемы можно:
- использовать файловую блокировку (`filelock`);
- перейти на SQLite или PostgreSQL;
- в будущем — использовать очередь задач или микросервисы.
