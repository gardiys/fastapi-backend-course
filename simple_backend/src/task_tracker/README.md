Минусы хранения задач в оперативной памяти:
1. Данные теряются при перезапуске приложения
2. При запуске в нескольких воркерах у каждого будет отдельный список, т.к. нет общей памяти между
процессами
3. Невозможно эффективно искать, фильтровать и т.д.


Выводы по хранению задач в файле
1. Теперь отсутствуют проблемы под п.1 и п.2 из прошлого раздела
2. Мы не избавились от хранения состояния, т.к. по-прежнему файл хранится
на нашем севере, а не на каком-то стороннем ресурсе
3. Задачи также можно хранить в:
   * БД (удобная фильтрация, но более сложная реализация и высокая ресурсоемкость);
   * Облачное хранилище (масштабируемость, но зависимость от внешних сервисов)
   * Кэш-системы (например, Redis) (быстрый доступ, но данные могут быть потеряны при перезапуске)


Проблемы, оставшиеся на этапе использования облачного сервиса:
1. Возможность возникновения состояния гонки
2. По-прежнему нет удобных способ поиска, фильтрации данных, которые предоставляют реляционные БД

Возможные решения:
По п.1: 
1. Использование специальных механизмов, позволяющих избежать состояния гонки, не давая обновлять данные,
если они устаревшие: если позволяет хранилище, использовать заголовки ETag, If-Match (при считывании данных
возвращается ETag, при запросе на обновление он отправляется в заголовке If-Match и если оказывается, что 
ETag с тех пор изменился, то запрос не пройдет)
2. Использование очереди задач: все запросы на изменение отправляются в очередь, воркер берет их из нее 
последовательно, тем самым позволяя обрабатывать ситуации, когда мы имеем дело с изменением данных на основании
уже неактуальной информации (т.к. они допустим изменились из-за прошлого запроса)

По п.2: использование реляционной БД
