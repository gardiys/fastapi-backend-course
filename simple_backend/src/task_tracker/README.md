# Хранение данных в оперативной памяти
## Плюсы
 - Высокая скорость доступа
 - Простота реализации полезно для тестирование или прототипирования
## Минусы
 - Данные в оперативной памяти теряются при перезагрузке приложения
 - Ограниченный объем памяти и дорогая память по сравнение с хранением на физическом носителе
 - Проблема с конкурентным доступом что требует блокировки  иди других механизмов синхронизации
 - Риски переполнения памяти
## Итог
    Рационально использовать данный подход если нужно что-то быстро протестировать либо показать реализацию ,
    какой-то задумки когда нету времени поднимать и набрасывать схему для бд или для фаила


# Улучшение приложения путем добавляние json фаила

### Улучшение после создания фаила json
    Теперь после перезагрузки или отключение приложения данные остаются .
### Изавились ли мы от хранения состояния
    Нет,полностью избавиться таким способом не удалось.
    Это все еще форма хранения состояния, но в персистентной (постоянной) форме, а не в волатильной (временной) памяти.
### Хранение данных 
- Можем хранить в базе данных локальной например sqllite (преимуществом является поддержка сложных операций к данным и схема данных)
- Облачная база данных например postgresql (преимуществом ялвяется масштабируемость,поддержка сложных операций ,а также доступность к этой базе данных вне приложения)
- In-memory базы данных например redis (преимуществоv является высокая скорость доступа)

# Состояние гонки
    Проблема состояния гонки это проблема когда в нашем случае корутины обгоняя друг друга могут записывать данные в одно место 

### Решение проблемы
    Использовать БД либо использовать блокировки,
    также возможно использование Optimistic update с версионированием - это когда перед проверкой смотрим не изменились ли данные
    с момента,когда их последний раз видели
